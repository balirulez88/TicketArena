# 54: Transaction timeouts and retries

**What to build:** under heavy contention a booking request never hangs and never fails with an opaque internal error: booking transactions run under bounded lock and statement timeouts, retryable conflicts retry the whole transaction, and contention the retry cannot absorb becomes a retryable `BOOKING_BUSY`, while failures that are not contention stay visible as internal errors. Spec: Holding seats (step 3); ADR 0005. Split from ticket 12 (part 1 of 4, see `issues/12-lock-timeout-and-deadlock-retry.md`). Owns TD-020 and TD-067 in `docs/technical-debt.md`.

**Reference only:** two rejected attempts of ticket 12 (branches `rejected/12-lock-timeout-and-deadlock-retry-20261106-132615` and `-20261106-165157`) may be read; their code and reviews count for nothing here.

Each criterion names its test and the sabotage that test must catch: making the stated change to the production code must turn that test red.

- [ ] Ground rules: every guarantee below that depends on Postgres, the `pg` driver, the Neon driver or Prisma is proved against the real test database or the real driver (ADR 0010), never against a hand-built error object or a proxied client. No existing assertion is removed or loosened. Every test this ticket adds or changes creates and disconnects its own clients (no module-level or lazily created client shared across test cases), never holds a lock or connection for a fixed time (blockers and occupiers are released by a latch the test opens), and bounds every wait on Postgres state with a deadline whose failure message names what it waited for. Behaviour tests may inject shorter timeouts than production; waits on real timeouts set per-test timeouts in the test file.
- [ ] Settings: `holdSeats` and `placeOrder` transactions run with `lock_timeout` 3s and `statement_timeout` 5s, local to the transaction. Test: a test-scoped trigger on a row each operation writes records `current_setting('lock_timeout')` and `current_setting('statement_timeout')` into a test table; with the service's default options both operations record `3s` and `5s`; afterwards a query on the same pooled connection (pool size 1) shows the server defaults. Sabotage: a different value, or a session-level setting, turns it red.
- [ ] One source of truth: one exported timeouts value (lock, statement, retries) drives both the `SET LOCAL` values and the Prisma transaction options (`bookingTransactionOptions(timeouts)`), and `apps/web/src/server/trpc.ts` builds the Prisma client and the booking service from that same value. Test: a test of the web composition asserts the client's transaction options and the service's timeouts come from one value. Sabotage: building either from a separate literal turns it red.
- [ ] Transaction budget: the Prisma `timeout` is at least (lock waits on the longest path, which is `placeOrder`: buyer advisory lock, hold row, seat rows) × `lock_timeout` + `statement_timeout` + a documented margin; `maxWait` is a documented value consistent with `acquireTimeoutMs`. Tests: a unit test pins that relation for the production values (sabotage: Prisma's default 5s timeout turns it red); a real-Postgres test builds a client from `bookingTransactionOptions` with shortened timeouts (injected `lock_timeout` at least 1s) and makes one `placeOrder` attempt wait on each of its three locks in turn, each blocker released once `pg_stat_activity` shows the service has waited at least 60% of `lock_timeout` on it (`clock_timestamp() - query_start`, polled with a deadline). The call succeeds with one committed order, `deadlock_retry` = 0 and no `P2028`; the test asserts it observed all three waits, and fails naming the wait if any ends in `55P03`.
- [ ] Retry set: exactly `40P01`, `55P03` and `40001` retry the whole transaction, up to 3 retries, each retry incrementing `deadlock_retry`; any other database error is not retried. Test: a unique violation raised inside the transaction runs exactly one attempt. Sabotage: retrying every error turns it red; dropping a code from the set turns its test below red.
- [ ] `55P03` exhaustion: a transaction blocked past `lock_timeout` makes 4 attempts and then fails with `BookingBusyError`, for `holdSeats` and for `placeOrder` (one test each), each asserting `deadlock_retry` = 3 and `booking_busy` = 1, with the blocker released by a latch only after the call has settled.
- [ ] `40P01` (AT-05): an induced deadlock against `holdSeats` is retried and the whole transaction then succeeds with exactly one committed hold and `deadlock_retry` = 1. The service is made the victim: the outside session closes the cycle immediately after `pg_blocking_pids` shows the service waiting on it, well within `deadlock_timeout`, with that wait raced against the service call so an early failure surfaces at once (not as a deadline miss). If the outside session is aborted instead, the test fails with a message saying so.
- [ ] `40001`: Postgres raises a real serialization failure inside the service's own `holdSeats` transaction on its first attempt only, through the real driver and Prisma: booking runs under READ COMMITTED, so a test-scoped trigger `RAISE ... USING ERRCODE = '40001'` gated on state that survives the rollback (for example `nextval` of a test sequence = 1). The transaction is retried and succeeds, the first attempt left no rows, `deadlock_retry` = 1; trigger and sequence use test-unique names and are removed afterwards.
- [ ] Classifier coverage: every field and branch of the error classifier is exercised by a real-database test above or here, covering errors from raw queries (`$queryRaw` / `$executeRaw`) and from Prisma model queries (which can arrive wrapped, for example as `P2034`); the classifier reads no field that no such test produces.
- [ ] Jitter: the delay before each retry comes from an injected random source and is awaited through an injected timer seam. Tests: with a fixed random source the exact delays are asserted; two different random values give different delays; with the default random source (the timer seam recording the requested delay, no wall-clock measurement) every delay lies inside the documented bounds. Sabotage: a constant delay turns the second test red.
- [ ] Worst case: an exported function computes the worst total time from the first attempt to `BOOKING_BUSY` from the timeouts, the retry count, `maxWait` per attempt and the maximum jitter. A test pins its value for the production defaults and, separately, each term it sums (lock/statement timeouts, retries, per-attempt `maxWait`, maximum jitter) by changing one input at a time. Sabotage: leaving out the per-attempt `maxWait` changes the value and turns the test red.
- [ ] Pool acquire timeout (`pg`): when the pool's only connection is occupied, `holdSeats` and `placeOrder` fail with `BookingBusyError` and count `booking_busy`, including a `placeOrder` that fails on its first pool read, before its hold or event is known; the occupier signals from inside its transaction that it holds the connection (no sleep). For that first-read failure the test asserts the exact `eventId` argument the metrics port receives (the key used while the event is not yet known); the choice of key is a decision the implementation makes and documents. The router maps `BookingBusyError` to tRPC `TOO_MANY_REQUESTS` with code `BOOKING_BUSY` for both procedures (router test each). Every read `placeOrder` makes outside its transaction, including the idempotency re-read after a duplicate-key error, goes through the same mapping (test: that re-read failing on a saturated pool is `BOOKING_BUSY`, counted).
- [ ] Transaction-start timeout, isolated: with `acquireTimeoutMs` longer than the test and a short `maxWait`, an occupied pool makes the service fail with `BookingBusyError` whose cause is the start-timeout `P2028`; with the two values swapped, the cause is the pool-acquire timeout. Each test asserts which cause it got. Sabotage: dropping the `P2028` start-timeout branch turns the first red.
- [ ] TD-067, `P2028` and the pinned messages: saturation is recognised from the pg-pool queue message `timeout exceeded when trying to connect` and the Prisma start-timeout message (`Unable to start a transaction in the given time`), both pinned in real-driver tests with the coupling noted next to the constants. A `P2028` raised because a transaction exceeded its own runtime timeout surfaces as an internal error with its cause after exactly one attempt (real-Postgres test through the service). A "Transaction already closed" `P2028` captured from Prisma (a transaction client used after its `$transaction` committed; not hand-built) is not saturation.
- [ ] Connection failures are not saturation: `createPrismaClient` applies `acquireTimeoutMs` to both drivers (the Neon pool's `PoolConfig` takes `connectionTimeoutMillis`). Against a local TCP listener that accepts and never answers, a `pg` client and a Neon client (test points `neonConfig.wsProxy` at it and restores it in `finally`) each fail within the bound with the pinned connect-timeout message `Connection terminated due to connection timeout`; the test asserts that message, not just any error. Those captured connect-timeout errors classify as internal errors, not `BOOKING_BUSY`, and count nothing. Sabotage: matching any "timeout" as saturation turns it red.
- [ ] SQLSTATE `57014`: a statement cancelled by `statement_timeout` (real Postgres, a test-scoped trigger running `pg_sleep` past an injected timeout inside the service's transaction) fails with `BookingBusyError` after one attempt and counts `booking_busy`; a statement cancelled by `pg_cancel_backend` from another session is not `BOOKING_BUSY`: the service rethrows an error keeping `57014` in its cause chain and the router returns `INTERNAL_SERVER_ERROR`. The field or message that tells them apart is pinned in both tests and the coupling noted next to it.
- [ ] Narrow public surface: `packages/booking/src/index.ts` exports only what code outside the package uses (the service, its errors and ports, `bookingTransactionOptions`, the default timeouts, the acquire timeout, the worst-case function and the metrics factory); constants only tests use are imported by tests from their module. Test: an allow-list test in `packages/booking` compares the runtime export names of `src/index.ts` (`Object.keys` of the module namespace) with an explicit sorted list of the permitted names, and fails naming both the unexpected and the missing exports. Types are not runtime exports, so the allow-list also covers them through a type-level check or a source-level export listing that fails on additions. Sabotage: exporting any extra name from `index.ts` (for example a test-only constant) turns it red; removing a permitted export turns it red too.
