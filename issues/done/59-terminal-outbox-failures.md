# 59: Terminal outbox failures

**What to build:** an outbox event that can never be published stops being retried forever: it reaches an explicit, terminal `FAILED` state that keeps its payload, failure reason and audit history, an operator is alerted and can recover it by a documented procedure, and the rest of its aggregate keeps moving, while a broker outage, however long, never fails a single row. Resolves TD-038 in `docs/technical-debt.md` (MEDIUM, CORRECTNESS, after an approved risk reassessment); must merge before tickets 25, 27 and 38, which are blocked by it. Spec: Messaging; ADR 0003, ADR 0011.

**Maintainer decision (2026-11-14):** later events of the same aggregate may progress after an event has permanently failed, consistent with the out-of-order-tolerant messaging architecture (the consumer-side DLQ in ADR 0011 already accepts the same gap). A failed event is never silently discarded, never deleted and never marked delivered: it stays `FAILED`, visible and recoverable, until an operator acts on it.

Scope: the relay (`packages/messaging/src/outbox-relay.ts`), every service's outbox store (booking, payment, notification), the worker's health endpoint, and the consumers of every event type an outbox can hold. Each criterion names its test and the sabotage that test must catch.

- [ ] Ground rules: every guarantee below is proved against the real test database and real NATS (ADR 0010); the broker outage is a real one (the test stops or disconnects the broker), never a hand-built error object. No existing assertion is removed or loosened. A schema change comes with a migration that passes ticket 49's drift test.
- [ ] Classification: a publish failure is permanent when it is specific to the row (no stream matches the row's subject; the payload exceeds the broker's maximum; the payload cannot be serialised) and transient otherwise (connection lost, PubAck timeout, broker unavailable, stream full). Tests against real NATS: a subject outside every stream and an oversized payload classify as permanent; a stopped broker classifies as transient. The errors or fields that tell them apart are pinned in those tests and the coupling is noted next to the constants. Sabotage: classifying every error as permanent turns the outage test below red.
- [ ] Explicit terminal state: a row whose publish fails permanently becomes `FAILED` once its permanent failures reach a documented, injectable cap, with `attempts`, `lastError` (the failure reason) and the time it failed recorded; the relay never claims a `FAILED` row again. Test for the booking and the payment outbox. Sabotage: leaving the row `PENDING` after the cap turns it red.
- [ ] Never discarded, never delivered: a `FAILED` row keeps its `payload` (the full envelope, unchanged byte for byte), its outbox id, aggregate and event type; it is never deleted, its `status` is never `PUBLISHED` and its `publishedAt` stays null; any retention rule for outbox rows excludes `FAILED` rows. Test: after the cap, the row read back equals the inserted row in every column except the failure bookkeeping, and nothing reached the broker under its id. Sabotage: marking the row `PUBLISHED` or clearing its payload at the cap turns it red.
- [ ] Audit history: every permanent publish failure and every status change of an outbox row (`PENDING` -> `FAILED`, and `FAILED` -> `PENDING` by a requeue, with the operator and the reason given) is recorded append-only with its time, attempt number and error, readable per outbox id. Test reads the history after the cap and after a requeue. Sabotage: overwriting the earlier entry instead of appending turns it red.
- [ ] An outage is never terminal: with the broker stopped for more ticks than the cap, no row becomes `FAILED` and transient failures do not count towards the cap; once the broker is back, every row is published, in order per aggregate. Sabotage: counting transient failures towards the cap turns it red.
- [ ] Aggregate progress (TD-038): with rows A1, A2, A3 of one aggregate and A1 failing permanently, A1 ends `FAILED` and A2 and A3 are then published in order; rows of another aggregate are published throughout, before A1 reaches the cap. Test asserts the publish order the broker received. Sabotage: a `FAILED` row that still holds its aggregate turns it red.
- [ ] Later events progress safely: for every aggregate that can have more than one event in one outbox (today `order` in the booking outbox: `order.placed`, then `order.confirmed`) and every consumer of those events, a test delivers a later event while an earlier event of its aggregate is `FAILED`, through the real consumer runner. The consumer either applies it correctly or refuses it without any partial state change (it is retried or dead-lettered under ADR 0011, never acknowledged with a wrong effect). The earlier event is then requeued and published, and the end state equals the end state of in-order delivery, with every side effect (rows written, payments, notifications) happening exactly once. Sabotage: removing a consumer's out-of-order guard, or its `processed_messages` check, turns one of these tests red.
- [ ] Idempotent recovery: a requeued event is published under its original outbox id (the `Nats-Msg-Id` consumers deduplicate on), so a consumer that already processed it, or receives it twice, changes nothing the second time. Test: deliver the requeued event twice; the consumer's effects and `processed_messages` count are unchanged by the second delivery. Sabotage: requeueing as a new outbox row with a new id turns it red.
- [ ] Manual recovery: an exported operation, with a script that calls it, requeues one `FAILED` row by service and outbox id, given the operator's name and a reason: the row becomes `PENDING` with its permanent-failure count reset and a history entry added. It refuses a row that is not `FAILED` (for example `PUBLISHED` or `PENDING`) and an unknown id, changing nothing, with a message naming the row and its status. Tests for the requeue and both refusals. Sabotage: allowing a `PUBLISHED` row to be requeued turns the refusal test red.
- [ ] Alerting: the transition to `FAILED` is logged exactly once at `error`, with the service, outbox id, aggregate type and id, event type, attempts and last error, and without the payload (ticket 51's redaction applies); repeated ticks before the cap do not log at `error`. Test counts the log lines. Sabotage: logging on every tick turns it red.
- [ ] Health metrics: an exported function returns, per service, the number of `FAILED` rows, the age of the oldest and the number of transitions to `FAILED` recorded in the history. The worker's `GET /health` body includes them and an alert flag that is set while any `FAILED` row exists, without failing its liveness status. Tests for the function (zero, one, several services) and for the health response with and without a `FAILED` row. Sabotage: dropping the flag or reporting a fixed zero turns them red.
- [ ] Every entry in `docs/technical-debt.md` whose Target is ticket 59 (TD-038) is `RESOLVED`, with the tests that prove it named in `Verification` (the host refuses the merge otherwise).

**Documentation deliverable (reviewed, not test-verified):**

- [ADR 0022](../docs/adr/0022-terminal-failed-outbox-events.md) already records the decided policy (accepted 2026-11-14, before this ticket's implementation); this ticket completes it and keeps it true: what counts as permanent, the cap, the `FAILED` state and what it preserves, that a `FAILED` row releases its aggregate (the consumer-side DLQ in ADR 0011 already accepts the same gap), and that failed events are never discarded or marked delivered. It lists, per aggregate with more than one event type, what each consumer does when a later event arrives before an earlier one; a new multi-event aggregate adds a row there.
- A runbook in `docs/messaging/` for a `FAILED` outbox event: the alert to watch (the `error` log line and the health flag), how to find and inspect the row and its history, how to decide (fix the cause, then requeue; or leave it `FAILED` with the reason recorded), the requeue command, how to confirm the event was published and consumed once, and what never to do (delete the row, set it `PUBLISHED` by hand, or re-insert it under a new id).
- `docs/messaging/index.md` describes the relay's new behaviour and replaces the sentence saying later rows wait for a failed earlier one; `docs/database/index.md` describes the `FAILED` status, what it keeps and the history.
