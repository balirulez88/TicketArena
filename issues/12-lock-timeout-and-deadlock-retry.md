Ground rules

- [ ] No existing assertion in the booking, hold-busy or router tests is removed or loosened. Every guarantee below that depends on Postgres, the `pg` driver or Prisma is asserted against the real test database (ADR 0010), never against a hand-built error object or a proxied client. Behaviour tests may inject shorter timeouts than the production defaults; tests that wait on real timeouts set their own per-test timeout in the test file.

Timeouts and the transaction budget

- [ ] Booking transactions (`holdSeats` and `placeOrder`) run with `lock_timeout` 3s and `statement_timeout` 5s, local to the transaction. A test reads `current_setting('lock_timeout')` and `current_setting('statement_timeout')` from inside a transaction the service itself opens with its default options (a test-scoped trigger on a row the service writes is the preferred observation point, not a production test seam) and asserts `3s` and `5s`; afterwards a query on the same pooled connection (pool size 1) shows the server defaults again.
- [ ] One exported function derives the Prisma interactive-transaction `timeout` from `lock_timeout` and `statement_timeout`, and sets `maxWait` to a documented value consistent with `acquireTimeoutMs`. Its `timeout` is at least (the number of lock waits on the longest path, which is `placeOrder`: buyer advisory lock, hold row, seat rows) × `lock_timeout` + `statement_timeout` + a documented margin. Every production client that runs booking transactions (`apps/web/src/server/trpc.ts`) is built with it. A unit test pins that relation for the production values. A real-Postgres test builds a client from the same function with shortened injected timeouts and makes one `placeOrder` attempt wait on each of its three locks in turn, each blocker released once `pg_stat_activity` shows the service has waited at least 60% of `lock_timeout` on it (`clock_timestamp() - query_start`, polled from Postgres, with a deadline). The injected `lock_timeout` is at least 1s. The call succeeds with one committed order, no retry (`deadlock_retry` = 0) and no `P2028`; the test asserts it observed all three waits, and if any wait ends in `55P03` it fails with a message naming that wait.
- [ ] `createPrismaClient` applies `acquireTimeoutMs` to both drivers (`pg` and the Neon pool, whose `PoolConfig` takes `connectionTimeoutMillis`), the production web client sets it, and a test proves the Neon client fails a query within the acquire timeout instead of waiting indefinitely (for example against a local TCP listener that accepts and never answers; the test may point `neonConfig.wsProxy` at it and must restore it afterwards). This criterion requires only a bounded failure, not `BOOKING_BUSY`: a Neon connect timeout is not pool saturation.

Retry

- [ ] `40P01`, `55P03` and `40001` retry the whole transaction up to 3 times; each retry increments `deadlock_retry`.
- [ ] `55P03`: a transaction blocked past `lock_timeout` is retried 3 times and then returns `BOOKING_BUSY`, for `holdSeats` and for `placeOrder`, and each test asserts `deadlock_retry` = 3 and `booking_busy` = 1.
- [ ] `40P01` (AT-05): an induced deadlock against `holdSeats` is retried and the whole transaction then succeeds, leaving exactly one committed hold, with `deadlock_retry` = 1. The test makes the service the victim (the outside session closes the cycle immediately after `pg_blocking_pids` shows the service waiting on it, well within `deadlock_timeout`; it may also raise its own `deadlock_timeout`, but the test must not rely on that alone, since it needs a superuser); if the outside session is aborted instead, the test fails with a message saying so.
- [ ] `40001`: Postgres raises a real serialization failure inside the service's own `holdSeats` transaction on its first attempt only, through the real driver and Prisma. Booking runs under READ COMMITTED, so a test-scoped trigger `RAISE ... USING ERRCODE = '40001'` is the expected way; "first attempt only" uses state that survives the rollback (for example `nextval` of a test sequence = 1). The whole transaction is retried and succeeds, the first attempt left no rows, and `deadlock_retry` = 1. The trigger and sequence are scoped to the test's own rows and removed afterwards.
- [ ] Retry jitter comes from an injected random source and the wait from an injected timer seam. With a fixed random source a test asserts the exact delay before each retry; with different random values the delays differ. `docs/database/index.md` states the delay bounds and the worst total time from the first attempt to `BOOKING_BUSY`, and a test with the default random source (the timer seam still recording the requested delay, no wall-clock measurement) asserts the delays stay inside those bounds.
- [ ] Every field and branch of the error classifier is exercised by a real-Postgres test, covering both errors raised by raw queries (`$queryRaw` / `$executeRaw`) and errors raised by Prisma model queries (which can arrive wrapped, for example as `P2034`); the classifier reads no field that no such test produces.

Saturation and timeouts that are not retried

- [ ] A pool acquire timeout returns `BOOKING_BUSY` (tRPC `TOO_MANY_REQUESTS`) and counts `booking_busy`, for `holdSeats` and for `placeOrder`, including a `placeOrder` that fails before its hold or event has been read. Both the service tests and the router tests (`apps/web/src/server/routers/booking.test.ts`) assert the error code and the `booking_busy` count; `docs/database/index.md` names the key the count goes to when the event is not yet known.
- [ ] TD-067: pool saturation is recognised by a test against the real driver (the message it matches is pinned, and the coupling is noted next to it). Saturation matches the transaction-start `P2028` positively ("Unable to start a transaction in the given time"), and a test shows a `maxWait` start timeout is `BOOKING_BUSY`. A `P2028` raised because a transaction exceeded its own runtime timeout surfaces as an internal error with its cause and is not retried (real-Postgres test through the service). A "Transaction already closed" `P2028` captured from Prisma (a transaction client used after its `$transaction` has committed; not hand-built) is classified as not `BOOKING_BUSY` by the classifier, which may live in a module `index.ts` does not export.
- [ ] SQLSTATE `57014`: a statement cancelled by `statement_timeout` (real Postgres, for example a test-scoped trigger running `pg_sleep` past an injected timeout) returns `BOOKING_BUSY` without a retry and counts `booking_busy`. A statement cancelled for any other reason (for example `pg_cancel_backend` from another session) is not `BOOKING_BUSY`: the service rethrows an error that keeps `57014` in its cause chain and the router returns `INTERNAL_SERVER_ERROR`. Both are tests; the message or field that tells them apart is pinned and the coupling is noted next to it. Spec step 3 (Holding seats) and `docs/database/index.md` record this `57014` rule.

Correctness the retry relies on

- [ ] TD-018: in `holdSeats`, a failure after the writes have begun (for example a failing outbox insert) leaves no hold, no claim and the seat `AVAILABLE`, both for a first attempt and for an attempt that is itself a retry (the first attempt failing retryably, for example with the `40001` trigger above).
- [ ] TD-016: the clock-after-lock test synchronises on Postgres (`pg_locks` / `pg_blocking_pids`) instead of sleeps. The blocker sets a flag only after `pg_blocking_pids` shows the service blocked by it, and immediately before it sends `COMMIT`; every clock read the service makes after its lock-free snapshot is stamped synchronously with the flag, and the test asserts every such read carries it (not only the last one). This is sound because a clock read taken before the lock happens before the service blocks, so before the flag. The TD-016 `Resolution` describes this mechanism and argument.

Test synchronisation

- [ ] TD-071: the saturation tests in `packages/booking/src/hold-busy.test.ts` and `apps/web/src/server/routers/booking.test.ts` wait for a signal from inside the occupying transaction instead of a fixed sleep.
- [ ] Blocker and occupier sessions never hold a lock or a connection for a fixed time: they are released by a latch the test opens once the service call has settled or once Postgres shows the state the test waits for (no fixed multi-second sleeps such as the previous attempt's 16s). A deliberate `pg_sleep` inside the service's own transaction to exceed an injected timeout is allowed. Every wait on Postgres state (for example polling `pg_stat_activity` until a backend is blocked) has a deadline that fails with a message naming what it waited for, and is raced against the call under test so an early rejection surfaces.
- [ ] Shared test synchronisation helpers (`occupy`, latches, blocked-backend polling) exist once, in one module (for example `packages/booking/src/testing/pg-sync.ts`, not named `*.test.ts`), exposed only through a `@ticketarena/booking/testing` subpath export, not from `packages/booking/src/index.ts`, and imported by both the booking and the router tests; it uses only `pg` and Prisma clients already available, adding no dependency. Each test creates and disconnects its own extra clients; no module-level, lazily created client is shared across test cases. (`packages/test-infra/` is protected and out of scope.)

Production wiring

- [ ] The web app's tRPC context supplies a real `BookingMetrics` in production: `createRedisBookingMetrics` over an Upstash REST client built from `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN`, validated at the boundary (a `parseServerEnv`-style function naming the offending field) and injected, never read inside packages. It adds no new dependency (a `fetch`-based `HINCRBY` call with a request timeout is enough). `booking_busy` and `deadlock_retry` both reach it. Tests prove the context passes the metrics through to the booking procedures and that the adapter sends `HINCRBY` with the bearer token (the HTTP boundary may be faked); a metrics failure or timeout never fails a booking. `docs/database/index.md` states the counters are best-effort (a request cut short by the platform may lose an increment).
